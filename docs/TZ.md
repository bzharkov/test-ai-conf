## 0. Контекст и правила работы

Ты реализуешь учебный проект (направление «Программная инженерия», ПГТУ). Это веб-сервис: пользователь пишет обычным текстом задачи и бюджет, например «ПК для игр в 1440p и монтажа до 120 000 ₽». Сервис с помощью LLM и рекомендательного модуля подбирает **2–3 готовые совместимые сборки ПК**, объясняет выбор и даёт уточнить сборку в ИИ-чате.

Проект планировался на команду из трёх человек (frontend, backend, ИИ), но делать его будет один человек с твоей помощью. Поэтому:

- Работай **по этапам из раздела 12**. Каждый этап должен давать работающий результат: `docker compose up` поднимает всё, что сделано на этот момент.
- После каждого этапа запускай тесты и линтеры, делай коммит с понятным сообщением и кратко пиши, что сделано и что проверено.
- **Не выдумывай данные о железе.** Характеристики комплектующих берутся только из каталога в БД. Если каких-то данных нет, явно помечай их как отсутствующие, а не подставляй правдоподобные значения.
- Если внешний ресурс недоступен (нет сети, API отвечает с ошибкой, формат данных отличается от описанного здесь), не останавливайся. Сделай fallback из раздела 5.4 и запиши проблему в `docs/KNOWN_ISSUES.md`.
- Все тексты интерфейса и ответы ИИ на **русском языке**. Код, идентификаторы и комментарии в коде пиши на английском.
- Секреты храни только в `.env`. В репозитории лежит `.env.example`.

## 1. Цель и критерии успеха

**Цель:** работающий веб-сервис, который по текстовому описанию задач и бюджета выдаёт готовые совместимые конфигурации ПК с обоснованием выбора и позволяет уточнять результат в диалоге с ИИ.

**Сборка считается успешной, если одновременно:**
1. все комплектующие совместимы по правилам из раздела 6;
2. итоговая стоимость не превышает бюджет;
3. конфигурация подходит под заявленную задачу: у игровой сборки сильная видеокарта, у сборки для монтажа много ядер и ОЗУ, и так далее;
4. в ответах ИИ нет комплектующих, которых нет в каталоге.

**Целевые метрики на наборе из 30 тестовых запросов (раздел 11):**
- 0 ошибок совместимости;
- 100 % сборок укладываются в бюджет (если бюджет физически достижим);
- ≥ 80 % сборок соответствуют задаче по автоматической эвристике;
- 0 «галлюцинаций» (упоминаний несуществующих компонентов);
- время формирования сборок без учёта стриминга объяснения: p50 ≤ 5 с, p95 ≤ 15 с.

## 4. Пользовательские сценарии

1. **Подбор.** Пользователь на главной вводит запрос (свободный текст) и при желании уточняет его фильтрами: бюджет (слайдер/поле), «нужен Wi-Fi», «маленький корпус», «AMD/Intel», «без видеокарты». Нажимает «Подобрать», видит 2–3 карточки сборок («Оптимальная», «Экономичная», «Максимум за бюджет»).
2. **Детали сборки.** Клик по карточке открывает страницу со списком компонентов, ключевыми характеристиками, ценами, итоговой стоимостью, расчётом мощности БП, отметкой «совместимость проверена» и текстовым объяснением выбора.
3. **Сравнение.** Пользователь выбирает 2–3 сборки и сравнивает их таблицей.
4. **ИИ-чат по сборке.** На странице сборки открыт чат. Можно спросить «почему эта видеокарта?», «можно дешевле?», «чем заменить процессор?». Ответ стримится по токенам. На вопрос о замене ИИ предлагает **2–3 аналога из каталога**, совместимых с остальной сборкой, с разницей в цене и производительности. Аналог можно применить кнопкой, после чего сборка пересчитывается и заново проверяется на совместимость.
5. **Уточнение запроса.** Если в запросе нет бюджета или он противоречив (например, «4K-гейминг за 30 000 ₽»), сервис не падает. Он либо подбирает с разумным бюджетом по умолчанию и пишет об этом, либо показывает предупреждение «бюджет недостаточен, ближайшая возможная сборка стоит X ₽».
6. **История.** Последние запросы и сборки хранятся по анонимному `session_id` (cookie/localStorage) и доступны в боковой панели. Регистрация не нужна.

## 5. Данные

### 5.1. Категории компонентов
`cpu`, `motherboard`, `ram`, `gpu`, `storage`, `cpu_cooler`, `psu`, `case`. Корпусные вентиляторы, ОС и периферия в проект не входят.

### 5.2. Источник характеристик: BuildCores OpenDB
- Открытая база характеристик комплектующих, лицензия **ODC-By 1.0**. Репозиторий на GitHub (`buildcores/buildcores-open-db` или актуальный адрес, его нужно проверить). Атрибуцию обязательно указать в футере сайта и в README.
- Скрипт `scripts/import_opendb.py`:
  1. скачивает или читает локальную копию базы (путь задаётся параметром или через `OPENDB_PATH`);
  2. **сначала изучает реальный формат файлов** и пишет маппинг полей OpenDB → наша схема (раздел 5.5) в отдельном модуле `catalog/opendb_mapping.py`;
  3. нормализует единицы (мм, Вт, ГБ, МГц), названия сокетов (`AM5`, `LGA1700`…), форм-факторы (`ATX`, `mATX`, `Mini-ITX`, `E-ATX`), типы памяти (`DDR4`, `DDR5`);
  4. отбрасывает записи без полей, критичных для совместимости, и пишет статистику: сколько импортировано и сколько отброшено по каждой причине;
  5. идемпотентен: повторный запуск обновляет записи, а не дублирует их.
- Можно ограничиться актуальными поколениями (например, CPU с 2020 года), чтобы каталог был обозримым.

### 5.3. Цены и наличие
Легального открытого источника цен нет, поэтому сделай **абстракцию провайдера цен**:
```python
class PriceProvider(Protocol):
    async def get_prices(self, component_ids: list[int]) -> dict[int, PriceInfo]: ...
```
Реализации:
- `CsvPriceProvider` читает прайс `data/seed/prices.csv` с колонками `sku_or_name, price_rub, in_stock, source, updated_at` и сопоставляет строки с компонентами по точному имени или нормализованному имени модели (fuzzy-match через `rapidfuzz` с порогом; несопоставленные строки попадают в отчёт);
- `MockPriceProvider` генерирует детерминированную цену по эвристике (категория + производительность + seed). Он **явно помечен в UI** как «ориентировочная цена (демо)».

В интерфейсе у каждой цены указан источник и дата. Компоненты без цены и не в наличии в подбор не попадают.

### 5.4. Fallback без сети: демо-каталог
`scripts/seed_demo.py` загружает вручную подготовленный каталог из `data/seed/*.json` — около 15–30 реальных популярных моделей в каждой категории с реальными характеристиками и ориентировочными ценами в рублях. Его хватает, чтобы весь пайплайн и все тесты работали без внешних источников. **Тесты должны опираться именно на демо-каталог.** Характеристики в нём заполняй только теми значениями, в которых уверен. Если сомневаешься в значении, не включай модель в каталог.

### 5.5. Схема БД (минимум)

```
components
  id              serial pk
  category        enum(cpu, motherboard, ram, gpu, storage, cpu_cooler, psu, case)
  brand           text
  model           text
  name            text            -- полное отображаемое имя
  specs           jsonb           -- полные характеристики (см. ниже)
  perf_score      real null       -- нормированная производительность 0..100 (cpu/gpu)
  price_rub       numeric null
  in_stock        bool
  price_source    text
  price_updated_at timestamptz
  source          text            -- 'opendb' | 'seed'
  source_ref      text            -- id/путь записи в источнике
  embedding       vector(384)
  search_text     text            -- текст, из которого считался эмбеддинг
  unique(category, brand, model)

requests        id, session_id, raw_text, parsed_requirements jsonb, created_at
builds          id, request_id, label, items jsonb, total_price, estimated_power_w,
                psu_recommended_w, score, explanation text, warnings jsonb, created_at
chat_messages   id, build_id, role, content, created_at
```

Индексы: по `category`, GIN по `specs`, HNSW (или IVFFlat) по `embedding`.

**Обязательные поля `specs` по категориям** (на них опираются правила совместимости):

| Категория | Поля |
|---|---|
| cpu | `socket`, `cores`, `threads`, `base_clock_ghz`, `boost_clock_ghz`, `tdp_w`, `has_igpu`, `memory_types[]` |
| motherboard | `socket`, `chipset`, `form_factor`, `memory_type`, `memory_slots`, `max_memory_gb`, `m2_slots`, `sata_ports`, `wifi` |
| ram | `type`, `capacity_gb_total`, `modules`, `speed_mhz` |
| gpu | `chipset`, `vram_gb`, `length_mm`, `tdp_w`, `slots` (толщина), `recommended_psu_w` (если есть) |
| storage | `type` (`nvme`/`sata_ssd`/`hdd`), `interface`, `form_factor` (`M.2`/`2.5`/`3.5`), `capacity_gb` |
| cpu_cooler | `type` (`air`/`aio`), `sockets[]`, `height_mm` (для air), `radiator_mm` (для aio), `tdp_rating_w` (если есть) |
| psu | `wattage_w`, `form_factor` (`ATX`/`SFX`), `efficiency` (80+ ...), `modular` |
| case | `supported_mb_form_factors[]`, `max_gpu_length_mm`, `max_cooler_height_mm`, `psu_form_factor`, `radiator_support_mm[]`, `bays_2_5`, `bays_3_5` |

### 5.6. Таблица производительности
OpenDB не содержит бенчмарков, а без них ранжирование невозможно. Сделай `data/perf_scores.csv` (`category, model_pattern, score, note`):
- score по шкале 0–100 относительно топовой модели в категории;
- у CPU две колонки: `score_gaming` и `score_multicore`;
- заполни для популярных моделей последних поколений (Ryzen 5000/7000/9000, Intel 12–14 gen и Core Ultra 200, GeForce RTX 30/40/50, Radeon RX 6000/7000/9000). Значения бери как **относительный порядок по общеизвестным обзорам**, а в `note` укажи, что это приблизительная оценка;
- для моделей без записи сделай эвристику (CPU: ядра × частота с поправкой на поколение; GPU: по чипсету/VRAM) и пометь `perf_estimated=true`.

## 6. Правила совместимости (жёсткие, модуль `compat/`)

Каждое правило — отдельная чистая функция `check_xxx(build) -> list[Issue]`, где `Issue = {code, severity: error|warning, message_ru, components[]}`. Сборка допустима, если в ней нет ни одного `error`.

| Код | Правило | Уровень |
|---|---|---|
| `CPU_MB_SOCKET` | `cpu.socket == motherboard.socket` | error |
| `RAM_MB_TYPE` | `ram.type == motherboard.memory_type` и тип есть в `cpu.memory_types` | error |
| `RAM_SLOTS` | `ram.modules <= motherboard.memory_slots` | error |
| `RAM_MAX` | `ram.capacity_gb_total <= motherboard.max_memory_gb` | error |
| `MB_CASE_FF` | `motherboard.form_factor ∈ case.supported_mb_form_factors` | error |
| `GPU_CASE_LEN` | `gpu.length_mm <= case.max_gpu_length_mm` | error |
| `COOLER_SOCKET` | `cpu.socket ∈ cooler.sockets` | error |
| `COOLER_HEIGHT` | для air: `cooler.height_mm <= case.max_cooler_height_mm` | error |
| `AIO_RADIATOR` | для aio: `cooler.radiator_mm ∈ case.radiator_support_mm` | error |
| `COOLER_TDP` | `cooler.tdp_rating_w >= cpu.tdp_w`, если рейтинг известен | warning |
| `PSU_CASE_FF` | `psu.form_factor` совместим с `case.psu_form_factor` (SFX в ATX допустим) | error |
| `PSU_POWER` | `psu.wattage_w >= psu_recommended_w` (раздел 7) | error |
| `NO_VIDEO` | нет GPU и `cpu.has_igpu == false` | error |
| `M2_SLOTS` | число M.2-накопителей `<= motherboard.m2_slots` | error |
| `DRIVE_BAYS` | 2.5/3.5-накопители помещаются в корпус | warning |
| `MISSING_DATA` | для проверки не хватает поля | warning (компонент с отсутствующими критичными полями в автоподбор не берётся) |

Покрой модуль unit-тестами: на каждое правило минимум один положительный и один отрицательный кейс.

## 7. Расчёт мощности БП (модуль `power/`)

```
estimated_power_w = cpu.tdp_w * k_cpu        # k_cpu = 1.25..1.5 с учётом boost (вынести в конфиг)
                  + gpu.tdp_w
                  + 50   (материнская плата)
                  + 5 * ram.modules
                  + 5 * nvme + 8 * sata_ssd + 10 * hdd
                  + 15 (вентиляторы/USB)
psu_recommended_w = max(ceil_to_50(estimated_power_w * 1.3), gpu.recommended_psu_w or 0)
```

Коэффициенты держи в конфиге. Расчёт должен показываться пользователю с разбивкой по слагаемым.

## 8. Пайплайн подбора

```
текст → [1] разбор LLM → Requirements (JSON)
      → [2] распределение бюджета по категориям (по профилю)
      → [3] отбор кандидатов из БД (SQL-фильтры + цены/наличие)
      → [4] сборка комбинаций (beam search) с проверкой совместимости
      → [5] скоринг и выбор 2–3 разнообразных сборок
      → [6] расчёт БП, итоговая цена, предупреждения
      → [7] объяснение LLM (RAG только по данным сборки) → валидация ответа
```

### 8.1. Разбор запроса (`llm/parser.py`)
LLM возвращает **строго JSON** по Pydantic-схеме. Используй `response_format` с JSON-схемой, если модель её поддерживает; если нет, извлеки JSON из текста. При невалидном ответе делай ретрай с текстом ошибки валидации, максимум 2 раза.

```python
class Requirements(BaseModel):
    use_cases: list[Literal["gaming", "office", "video_editing", "3d_render",
                            "programming", "study", "streaming", "ml"]]
    primary_use_case: str
    budget_rub: int | None
    budget_is_strict: bool = True
    gaming: GamingReq | None        # resolution: 1080p|1440p|4k, target_fps, titles[]
    preferences: Preferences        # cpu_brand, gpu_brand, form_factor: any|compact|mini_itx,
                                    # wifi_required, min_ram_gb, min_storage_gb, quiet, rgb
    must_include: list[str] = []    # явно названные модели
    exclude: list[str] = []
    notes: str | None
    confidence: float               # 0..1
```

Также нужен **детерминированный fallback-парсер** на регулярках и словарях («до 120к», «120 000 ₽», «1440p», «монтаж», «игры» …). Он нужен, если LLM недоступна, и в тестах. Результаты LLM и fallback-парсера сливаются: явно найденные числа из regex (бюджет) приоритетнее. `must_include` резолвится в компоненты каталога через векторный и fuzzy-поиск. Если модель не нашлась, выдай предупреждение, а не выдумывай её.

Кэшируй результат парсинга в Redis по хэшу нормализованного текста (TTL 24 ч).

### 8.2. Распределение бюджета (`recommender/budget.py`)
Для каждого профиля задай в конфиге (YAML) доли бюджета по категориям с допуском ±. Ориентир для `gaming`: GPU 35–45 %, CPU 15–20 %, MB 10–12 %, RAM 7–9 %, storage 6–8 %, PSU 6–8 %, case 5–7 %, cooler 2–4 %. Для `video_editing`/`3d_render` доля CPU и RAM выше, для `office`/`study` допустима сборка без дискретной GPU при CPU с iGPU. При нескольких задачах доли смешиваются с весами, у главной задачи вес больше.

### 8.3. Отбор кандидатов
SQL-фильтры по категории, цене (в окне доли бюджета), наличию, предпочтениям (бренд, Wi-Fi, форм-фактор). По каждой категории бери top-N (N≈8–15) по соотношению `perf_score / price` с учётом профиля.

### 8.4. Сборка комбинаций
Beam search по порядку `cpu → motherboard → ram → gpu → cooler → case → psu → storage`. Несовместимые ветки отсекай сразу правилами из раздела 6. Ширина beam и лимит времени задаются в конфиге. Если в бюджет ничего не влезает, ослабь мягкие предпочтения, а если и это не помогло, верни ближайшую по цене допустимую сборку с флагом `over_budget` и объяснением.

### 8.5. Скоринг и разнообразие
```
score = Σ w_profile[k] * norm_perf[k]       # gaming: GPU и score_gaming CPU; монтаж: score_multicore, RAM
      + w_value * (1 - total/budget)        # экономия
      - penalties (bottleneck, warnings, перекос бюджета)
```
Штраф за bottleneck: сильный дисбаланс CPU/GPU относительно профиля и разрешения (в 4K CPU важен меньше). Итоговые 2–3 сборки должны **различаться**: «Оптимальная» (max score), «Экономичная» (≈70–85 % бюджета, лучший score/цена), «Максимум» (максимальный perf в бюджете). Если две сборки отличаются меньше чем двумя ключевыми компонентами, вторую замени следующей по рейтингу.

### 8.6. Объяснение (`llm/explain.py`)
В промпт передаются **только** JSON сборки (компоненты, характеристики, цены, perf_score, расчёт БП, предупреждения) и `Requirements`. Системный промпт требует:
- опираться только на переданные данные;
- не называть моделей вне сборки;
- явно говорить «нет данных», если вопрос выходит за данные;
- держать структуру: «Под какую задачу», «Почему этот CPU/GPU», «Баланс и запас», «Что можно улучшить».

Объяснение генерируется после выдачи карточек и подгружается стримом. Подбор не должен ждать LLM.

### 8.7. Валидация ответов LLM (анти-галлюцинации)
Пост-проверка любого ответа модели:
1. извлеки из текста упоминания моделей: регулярки по паттернам вида `RTX \d{4}`, `Ryzen \d \d{4}X?3?D?`, `Core i\d-\d{4,5}`, `Core Ultra \d \d{3}` и т. п., плюс fuzzy-сверка с каталогом;
2. каждое упоминание должно быть в сборке или в переданном контексте аналогов;
3. при нарушении перегенерируй ответ со списком запрещённых упоминаний (1 раз), а если не помогло, удали предложение и добавь пометку.

Счётчик нарушений пиши в лог и в метрики оценки.

## 9. ИИ-чат и аналоги (RAG)

### 9.1. Эмбеддинги
`scripts/build_embeddings.py` строит `search_text` для каждого компонента (категория, бренд, модель, ключевые характеристики текстом) и считает эмбеддинг моделью e5 на CPU. Для e5 используй префиксы `passage: ` и `query: `. Сохраняй в `components.embedding`.

### 9.2. Поиск аналогов (`rag/alternatives.py`)
`find_alternatives(build, slot_category, intent: cheaper|better|similar, k=3)`:
1. кандидаты той же категории: векторная близость к текущему компоненту + фильтр по цене в зависимости от intent;
2. каждый кандидат подставляется в сборку и прогоняется через **все правила совместимости** (включая пересчёт БП);
3. результат — `{component, price_delta_rub, perf_delta_pct, compat_ok, notes}`; несовместимые варианты отбрасываются.

### 9.3. Чат (`llm/chat.py`)
- Эндпоинт со стримингом **SSE**. События: `token`, `alternatives` (структурированный список карточек аналогов), `done`, `error`.
- Используй tool calling, если модель его поддерживает; если нет, сначала классифицируй намерение отдельным коротким вызовом и затем вызывай функции бэкенда сам. Инструменты:
  - `get_build()` — текущая сборка;
  - `find_alternatives(category, intent)`;
  - `search_catalog(query, category?)` — векторный поиск, только для справки;
  - `check_compatibility(replacements)`.
- Контекст: системный промпт + JSON сборки + `Requirements` + последние 10 сообщений. Ответ проходит валидацию из 8.7. Аналоги, полученные через инструмент, считаются допустимыми упоминаниями.
- Кнопка «Применить замену» вызывает отдельный REST-эндпоинт, а не чат. Сервер пересобирает и перепроверяет сборку.

## 10. API (контракт)

Все ответы в JSON, ошибки в формате `{error: {code, message}}`. Документация OpenAPI доступна на `/docs`. Префикс `/api/v1`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/configure` | `{text, filters?, session_id}` → `{request_id, requirements, builds[], warnings[]}` |
| GET | `/builds/{id}` | детальная сборка: компоненты, проверки совместимости, расчёт БП |
| GET | `/builds/{id}/explanation/stream` | SSE-стрим объяснения (кэшируется после генерации) |
| POST | `/builds/{id}/replace` | `{category, component_id}` → новая сборка (новый id) + результат проверок |
| GET | `/builds/{id}/alternatives?category=&intent=` | аналоги без чата |
| POST | `/builds/{id}/chat` | `{message}` → SSE-стрим ответа |
| GET | `/builds/{id}/chat` | история чата |
| POST | `/compare` | `{build_ids[]}` → таблица сравнения |
| GET | `/components?category=&q=&limit=` | поиск по каталогу |
| GET | `/components/{id}` | карточка компонента |
| GET | `/history?session_id=` | история запросов |
| GET | `/health` | статус БД, Redis, LLM, размер каталога |

Rate limit на `/configure` и `/chat` через Redis (например, 20 запросов в минуту на session_id). Таймаут вызова LLM 30 с. При недоступности LLM `/configure` работает через fallback-парсер и отдаёт `warnings: ["llm_unavailable"]`.

Pydantic-схемы ответов → сгенерируй TypeScript-типы для фронтенда (`openapi-typescript`), чтобы контракт не расходился.

## 11. Frontend

### 11.1. Страницы
- **`/` Главная.** Крупное поле ввода запроса с примерами-подсказками (кликабельные чипы: «Игры в 1440p до 120 000 ₽», «Офисный ПК до 40 000 ₽», «Монтаж 4K до 200 000 ₽», «Компактный ПК для учёбы и Dota 2»). Блок дополнительных фильтров сворачивается. Ниже показан результат: карточки сборок.
- **Карточка сборки:** название-ярлык, итоговая цена и доля от бюджета, ключевые компоненты (CPU, GPU, RAM, накопитель), бейдж «Совместимость проверена ✓» или предупреждения, кнопки «Подробнее» и «Сравнить».
- **`/build/:id` Сборка.** Слева таблица компонентов: категория, модель, ключевые характеристики, цена с источником, кнопка «Заменить» (открывает панель с 2–3 аналогами), блок «Питание» с разбивкой расчёта, блок «Проверки совместимости» (список правил с ✓/⚠). Справа ИИ-чат: стриминг по токенам, рендер markdown, карточки аналогов внутри сообщения с кнопкой «Применить», а сверху объяснение выбора.
- **`/compare` Сравнение.** Таблица из 2–3 сборок по категориям, различия подсвечены.
- **Боковая панель/страница «История».**

### 11.2. Требования
- Адаптивность: корректно на ширине 360 px, 768 px и 1440 px.
- Состояния загрузки (skeleton), ошибок и пустого результата. Пока идёт подбор, показывай этапы: «Разбираю запрос → Подбираю комплектующие → Проверяю совместимость».
- Тёмная и светлая тема (по системной).
- Отображение распознанных требований («Я понял: игры 1440p, бюджет 120 000 ₽, Wi-Fi не обязателен») с возможностью поправить их и пересобрать.
- Футер: атрибуция BuildCores OpenDB (ODC-By 1.0) и пометка, если цены демонстрационные.
- Визуальный стиль: аккуратный, «технический», без шаблонного вида. Дизайн-решения зафиксируй в `docs/ARCHITECTURE.md`.

## 12. Этапы реализации и критерии приёмки

**Этап 1. Каркас.** Монорепо, docker compose (db с pgvector, redis, backend, frontend), конфиг, `/health`, Alembic-миграции, CI-скрипт `make check` (линтеры + тесты), README с запуском.
*Приёмка:* `docker compose up` поднимает всё, `/health` зелёный, фронтенд открывается.

**Этап 2. Каталог.** Схема БД, демо-каталог (`seed_demo.py`), импорт OpenDB с маппингом, провайдеры цен, `perf_scores.csv`, эндпоинты `/components`.
*Приёмка:* в демо-каталоге каждая категория заполнена; импорт OpenDB печатает статистику; повторный импорт не создаёт дублей.

**Этап 3. Совместимость и питание.** Модули `compat/` и `power/` с полным набором unit-тестов.
*Приёмка:* все правила из раздела 6 покрыты тестами, тесты зелёные.

**Этап 4. Ядро подбора.** Fallback-парсер, бюджет по профилям, отбор, beam search, скоринг, разнообразие, `/configure`, `/builds/{id}`, `/replace`, `/compare`. Пока без LLM.
*Приёмка:* на 10 запросах из `eval/queries.yaml` с fallback-парсером получаются валидные сборки в бюджете; время подбора p95 ≤ 5 с.

**Этап 5. LLM.** Клиент OpenRouter (через SDK `openai` с `base_url` OpenRouter), парсер запроса через LLM со схемой и ретраями, объяснения со стримингом, валидатор галлюцинаций, кэш в Redis. Для тестов используй мок LLM-клиента, реальные вызовы не нужны.
*Приёмка:* при заданном ключе запросы разбираются LLM; без ключа всё работает через fallback; валидатор покрыт тестами.

**Этап 6. RAG и чат.** Эмбеддинги, поиск аналогов с проверкой совместимости, чат с инструментами и SSE.
*Приёмка:* в ответ на «чем заменить видеокарту подешевле» в чате появляются 2–3 совместимых аналога из каталога; «Применить» пересобирает сборку.

**Этап 7. Frontend.** Все страницы из раздела 11, типизированный клиент, стриминг. Фронтенд можно начинать параллельно с этапом 4, используя моки по контракту.
*Приёмка:* полный сценарий из раздела 4 проходит вручную; vitest-тесты на ключевые компоненты; на 360 px нет горизонтального скролла.

**Этап 8. Оценка качества.** `eval/queries.yaml` — 30 запросов: игровые, офисные, монтаж, учёба, плюс краевые случаи (без бюджета, нереалистичный бюджет, конкретные модели, «компактный», «без видеокарты»). У каждого запроса есть ожидания для автопроверки: бюджет, обязательная дискретная GPU да/нет, минимум RAM, минимальный perf GPU/CPU, форм-фактор. `run_eval.py` прогоняет все запросы (с LLM и без) и пишет `docs/EVAL_REPORT.md`: таблицу по каждому запросу (совместимость, бюджет, соответствие задаче, время, число галлюцинаций в объяснении) и сводные метрики из раздела 1.
*Приёмка:* отчёт сгенерирован; найденные проблемы исправлены или описаны в `KNOWN_ISSUES.md`.

**Этап 9. Доводка и деплой.** Production-сборка фронтенда (nginx), `docker-compose.prod.yml`, инструкция по деплою на VPS, сид-данные, скриншоты в README, краткая документация для защиты (архитектура, пайплайн, метрики).

## 15. Нефункциональные требования

- Логи в JSON с `request_id`; в лог пишутся время каждого этапа пайплайна и токены LLM.
- Всё, что касается подбора, детерминировано при одинаковом каталоге и требованиях (фиксируй seed, сортируй стабильно). LLM влияет только на разбор запроса и тексты.
- Покрытие тестами модулей `compat`, `power`, `recommender`, `llm/parser` (fallback), `llm/validator` не ниже 80 %.
- Никаких реальных вызовов LLM и сети в тестах.
- Ключи и персональные данные в логи не попадают.
